### 两级 IA 的两个决定

**顶层只有 `产测开发` / `运行监控`。** `system` 不是第三个模式,从账号下拉进入;
但它的页面**仍然是菜单行**,由服务端按 `admin:read` 求值。

这里和规格 §4.4 有冲突——§4.4 把用户管理/角色权限放进下拉。两者都保留:
下拉项**只跳转**到菜单用的同一路径,自身不带 fetch、不带权限判断,
所以「某页能否到达」只有一个真相来源,`test_admin_pages_in_menu.py` 仍然成立。

**种子改成同步而非插入。** 同步 `route_path` / `name` / `icon` / `parent_id`,
并把种子外的 app/menu **置 `is_active=False`**。不这样做的后果是:改了菜单名不会生效,
而旧的 `node-mgmt` / `flow-mgmt` / `exec-monitor` 会永远留着。

每个分组的 `required_permissions` 取**子页权限的并集**。分组填 `None` 会被权限过滤器
读成「对所有人可见」——只读角色因此看到 8 个空侧栏标题。空分组会被剪掉。

### 术语只改工位这一层

`流程节点模板`(流程节点)与 X6 画布节点**保留「节点」**——它们确实是节点,
把它们和工位混为一谈才是要消除的歧义。改的是:

* worker 页 → **工位执行器**(`WorkerRegistry.vue`)
* `NodeFlowBinding.vue` → **工位管理**(`StationManagement.vue`)
* 原 `StationManagement.vue`(worker 页)→ `WorkerRegistry.vue`

`FixtureDesigner.vue:476` 的 `注册节点` 在 `loadTopology` 内,是 X6 图节点,刻意不动。

`tests/cloud/test_station_terminology.py` 双向锁定:工位不得叫节点,
流程节点模板不得跟着被改。该测试匹配前先 strip 注释——`节点流程绑定` 作为历史说法
合理地留在 `router/index.ts` 与 `apps.py` 的注释里。

## 2. 上下文选择器:产品类型这一级的来源

**这一节记录一处被自己写错、后来改掉的跨仓结论。**

原先文档写的是「型号与产品类型之间没有任何键,真正的映射在 ATERag 的 registry 里,
要等 P4 的 bundle 契约才到得了」。**前半句对,后半句错。** 错的那半句是承重的——
它让上下文只交付了一级,而规格 §4.2 要两级。

映射一直存在:

* `ATERag/src/aterag/registry.py` —— `ProductEntry{domain, doc_number, doc_version}`
  按 `model_id` 建索引,持久化为 YAML;
* `ATERag/src/aterag/mcp_server/server.py:610` —— `list_models` 工具返回
  `{products: {型号: 产品类型}, domains: {产品类型: 状态}}`;
* 该工具**早已**在 ATERag 的只读 MCP 白名单 `ALLOWED_TOOLS` 里。

缺的是 ATEStudio 这一侧的接线,不是数据。

`services/aterag_catalog.py` 经**只读 MCP**取这一级(D2/D6:不去读 ATERag 的 YAML
或它的库,那会造一条没有鉴权也没有版本约束的私线)。它复用已有的 `_fetch_tools`,
因为 `MultiServerMCPClient` 没有 `call_tool` 方法,而且那个 helper 已经把 MCP 的
`BaseExceptionGroup`(`anyio` TaskGroup 的失败形态)转成调用方分支的错误类型。

### 降级是说出来的,不是静默的

| 情况 | `product_type` | `catalog_source` | 界面表现 |
|---|---|---|---|
| ATERag 可达且认识该型号 | 值 | `aterag-mcp` | 两级联动 |
| ATERag 可达但不认识该型号 | `null` | `aterag-mcp` | 该型号仍在型号列表里,只是产品类型为空 |
| ATERag 不可达 | `null` | `unavailable` | 该级**保留但置灰**,tooltip 说明原因 |

第三种是最要紧的:那一级如果悄悄消失,会被读成「设计就是单级」。
`catalog_warning` 带上原因,前端据此说明。

`product_type` **绝不**从型号代码推断。从代码前缀猜出来的东西会看起来对而且是错的。

`GET /api/v1/models` 本身提前于 P4 落地,因为选择器绕不过去。它按 `test_requirements`
聚合而不建 products/models 表:型号存在,当且仅当它有需求。`draft_conditions` 是
**待签数**——数出还有多少条条件**没有**被签字。红线是「未批准的条件不得作为产测判据」,
这里方向相反;把它算成「已就绪」才是违规。签字走 approve 端点(必填 `by`),本端点只读。

## 3. 顺带修掉的三个真问题

1. **分组 `required_permissions: None` 绕过权限过滤**——只读角色看到 8 个空侧栏标题。
2. **`test_menu_routes_resolve.py` 有假阳性洞**——404 兜底 `/:pathMatch(.*)*` 让任何
   单段 tail 都「能解析」,所以把菜单改成 `/ops/faultcase` 也能过,尽管该路由不存在。
   已补反向断言。
3. **操作员面板指向假工位 id**——`/operator/default` 这个工位不存在。已从菜单移除,
   路由保留,改由工位列表按行进入。

### 3.1 板端发现的一个既有问题(不在 P2 范围,但影响可用性)

菜单的 `required_permissions` 用的是**细粒度**词汇(`knowledge:read`、`flow:read`、
`node:read`、`system:read`),而 `ROLE_SCOPES` 只发**粗粒度**的
(`read` / `write` / `execute` / `admin` / `aterag:import`)。`get_current_user` 拿
**token 里的** scope 做比较,而 token 是登录时由 `get_effective_scopes` 烤进去的,
那个函数只看 `ROLE_SCOPES` 加上 `User.scopes` 这一列。

后果:**除 admin 外,任何账号登录后侧栏都是空的**——因为 `read` 匹配不上任何一条菜单
权限。admin 能看到全部,靠的是 `SCOPE_ADMIN`(`is_superuser`)这个「不做权限检查」的
旁路,不是靠权限匹配。

`auth/rbac.py` 的模块文档已经把这个陷阱记下来了(它举的例子是 `aterag:import`
曾不在任何角色的列表里,导致**所有人**包括 admin 都 403)。但它没有指出
**菜单这一侧的词汇与角色词汇根本不相交**——admin 是靠旁路活下来的,不是靠匹配。
这意味着权限体系目前实际上是「只有 admin」,`read` / `write` / `execute` 三个角色
在菜单上没有任何行为差异。

板上实测印证:`/register` 建出来的 `read` 用户 `scopes: []`,看到 0 个模式;
手工授 `flow:read` 后只看到 2 个分组。**这不是 P2 引入的**,P2 的分组并集与空分组
剪枝在这套词汇下工作正常(见 §4)。修它需要先决定:是给 `ROLE_SCOPES` 补齐
细粒度 scope,还是把菜单权限降到粗粒度。这是独立一件事,应当单独立项。

### 板端部署踩到的坑(照抄可省一小时)

* **仓库属主是混的。** `/opt/atestudio` 顶层属 `atestudio`,但上一轮部署把
  `.git/HEAD`、`.git/index`、大批 `.git/objects/*`、`pyproject.toml`、`uv.lock`
  留成了 **root 属主**,于是 `git fetch` 报「权限不足,无法在仓库对象库中添加对象」。
  修法:`chown -R atestudio:atestudio /opt/atestudio`。
* **`atestudio` 的家目录是 `/var/lib/atestudio`,不是 `/home/atestudio`**(后者不存在)。
  `npm` 会因写不了 `/home/atestudio/.npm` 而失败。
* **`UV_CACHE_DIR` 不能用 `/tmp/uvcache`** —— 那个目录属 `rpdzkj`,`atestudio` 写不进去,
  `uv` 直接拒绝启动。改用 `/var/lib/atestudio/.cache/uv`。
* **`scripts/deploy/deploy_cloud.sh` 对这台板子已经过期,不要用。** 它写死
  `EXPECTED_HEAD="d1e2f3a4b5c6"`,而当前头是 `f2b3c4d5e6a7`,会在迁移前主动 abort;
  它的目标目录是 `~/ATEStudio`(声明为 non-git rsync 目标),而实际部署是
  `/opt/atestudio` 的 git 检出。**这个脚本需要单独修一次**,本轮没动它。
* **bash 脚本里 `set -e` 配管道抓不住失败** —— `git fetch | tail` 的退出码是 `tail` 的。
  必须加 `set -o pipefail`,否则失败会被静默吞掉然后继续往下跑。
* 板端已用 `git checkout dev` 从游离 HEAD 切回分支,免得下次部署又游离。
* 验证用的临时用户(`p2-verify-read`)已删除,板上只剩原有的 `e2e-operator` 与 `chenjun`。

## 5. 环境陷阱(留给下一个人)

* `edit` 工具在部分文件上会反复 oldString 匹配失败(疑似行尾)。改用
  `[IO.File]::ReadAllText/WriteAllText` 或 Python 脚本精确替换。
* 提交消息必须用 `-F` 消息文件(PowerShell 处理多行 `-m` 不可靠)。
* **提交前先 `git reset` 清空索引**。否则 `git commit -- <path>` 会把索引里已 stage 的
  其他文件一并带上——本轮第一次提交就这样被污染了(4 文件 1264 行,而非 1 文件)。
* `git stash@{0}` 是早前会话遗留(`chore: finalize architecture-optimization plan`),
  **不要 pop**(会冲突中止但保留)。
* PowerShell 会吞掉 SSH 命令里的引号 → 用脚本文件 `scp` 后 `bash` 执行。
* ATERag 本地 `master` 的 upstream 被配成 `origin/main`,但那 6 个提交实际在
  `origin/master` 上,`origin/main` 落后 7 个。推送用 `git push origin master:master`。
  分支策略未统一,待定。
